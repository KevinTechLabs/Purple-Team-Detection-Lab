# Gap: T1098.004 — SSH authorized_keys (missed)

## What was tested
Atomic Red Team T1098.004 test 1 adds an attacker-controlled public key to an
`authorized_keys` file, then the `-Cleanup` step removes it.

## Why FIM missed it
The agent watches `/root/.ssh`, `/home/*/.ssh` and friends with `realtime="yes"`.
Real-time FIM is driven by the kernel inotify queue, but the add-then-remove
happened inside a single short window, and the net file state after cleanup was
unchanged. The modification wasn't surfaced as a syscheck alert in the test
window.

## Why it matters
A real persistence actor leaves the key in place, so FIM *would* fire on a genuine
intrusion. But a detection that depends on the file still being there at scan time
is fragile — an attacker who adds a key, uses it, and removes it would evade it.

## Fix (planned)
Catch the **action**, not just the resulting state:

- auditd watch on the key files for write/attr:
  `-w /root/.ssh/authorized_keys -p wa -k T1098_ssh_key`
  (file-level `-w`, which logs the write syscall even if the file is later removed)
- Pair it with a Wazuh rule on that key, same pattern as the other auditd rules.

This moves T1098.004 from "depends on file state" to "logged the moment the key
was written," which is the more reliable detection.
